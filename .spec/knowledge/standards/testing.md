# 测试与验收

测试政策只写在本文；TDD 的做法见 `test-driven-development` 技能，什么时候合并、什么时候审见 `.spec/rules/system.md`「工作方式」。

## 两种模式和判据

SDD / TDD 两种模式，写计划时先定走哪种：在计划开头用一句话写明、说明为什么；拿不准问用户。

- **SDD（快速模式，默认）**：契约先行、并行开发、写完就合。边界清楚、约定好接口就能各自做的走这个：新界面、新关卡、新道具、按现有模式扩内容。
- **TDD（测试先行）**：先列边界、写测试、再实现。边界多、出错代价大、靠试玩难发现的走这个：战斗结算、技能和状态叠加、复杂界面的状态和流程、联机同步、存档格式升级、经济系统。
- 两头都沾、或判断不了：问用户。

## 测什么

写成自动测试的：规则（胜负判定、技能和状态叠加）、数值（伤害与成长公式、掉落、经济）、配表（读进来先校验字段、类型和引用）、存档（读写和旧版本升级），以及复杂界面的状态和流程。

界面上**能量出来的行为也要测**，不因为「界面不自动化」就跳过：

- 动效：起点、终点的位移和播完后的终态（只断言「在播放」或时长，会漏掉配了动画却没动的情况）。
- 适配：各标准尺寸下控件在安全区里、互不遮挡。
- 交互：按钮能不能点到（没被盖住、在屏幕里），输入限制（如最大长度）生效。
- 生命周期：界面关掉以后，晚到的回调不再碰它。

## 靠看和试玩的

- **界面长什么样**：固定几个标准尺寸截图，对照美术一页纸（`.spec/knowledge/art/README.md`）看。Agent 先按截图验第一遍，再请用户看；还原设计稿的界面按 design-review 技能「视觉验收」的维度和容差逐条登记。
- **手感、好不好玩**：试玩。交付时给用户一份试玩清单：试什么、怎么试、看什么。

## 什么时候跑

- **SDD**：开发中、合并前都不跑；计划全部合完以后统一跑一次全量。验收测试照写，不跑。
- **TDD**：开发中可以跑，只跑这次新写的测试；全量回归同样留到计划合完统一跑一次。

## 回归用例

计划合完那一遍查出的 bug，能自动复现的（数值、规则）修的时候补一条回归用例；界面长相和手感类不补。值不值得记进 bug 墙，按 `.spec/knowledge/bug-wall.md` 开头的判据。

## 验证证据

底线和证据怎么写见 `.spec/rules/system.md`「工作方式·底线」。

## 验收标准（Definition of Done）

- [ ] 计划合完后，收口门槛命令跑过并贴了输出（命令见 `.spec/AGENTS.md`「收口门槛」）。
- [ ] 走 TDD 的部分，边界清单里每条都有测试。
- [ ] 界面和手感类改动附了截图或试玩清单；还原设计稿的界面附了「视觉验收」表（见 design-review）。
- [ ] 相关知识文档已更新（见 [`workflow.md`](./workflow.md)）。
