# 引导话题（第二段）

按下表顺序聊，跳过已经没有「待完善」的话题。配表依赖玩法，所以玩法在前。每个话题只补表里那个文件；用户拍板后用对应技能写进去，删掉那条「待完善」，方向级的取舍记 ADR（`.spec/decisions/`）。

| 顺序 | 话题 | 补全的文件 | 用哪个技能 |
| --- | --- | --- | --- |
| 1 | 玩法 | `.spec/knowledge/features/product-direction.md` | design-director → design-doc |
| 2 | 配表 | `Config/README.md`：有哪些表、什么格式、怎么命名 | design-doc |
| 3 | 美术风格 | `.spec/knowledge/standards/art-direction.md`、`Art/README.md` | art-director → art-bible |
| 4 | 策划 | 策划案怎么写、需求怎么拆：`.spec/knowledge/features/_TEMPLATE.md` | design-doc |
| 5 | 测试 | `.spec/knowledge/standards/testing.md` | — |
| 6 | 工作流 | `.spec/knowledge/standards/workflow.md`：分支、提交、怎么派 Agent | — |
| 7 | 其他规范 | `.spec/knowledge/standards/code-style.md`、`.spec/rules/project.md` | spec-steward |

## 1. 玩法

- **先问什么**：玩家为什么愿意再来一局？一局多长、几个人？在手机还是电脑上玩、怎么操作？有没有对标的游戏？
- **写到哪里**：按 design-director 的流程定方向（2-3 个候选方向，用户选一个），提炼 3-5 条产品支柱，定最小验证切片；再用 design-doc 写进 `product-direction.md`，把 `status` 保持为 `设计中`。一句话定下来后，同步改 `.spec/AGENTS.md`「项目是什么」和 README 里的那句话。
- **聊不完时**：支柱和核心循环定了就够，规格和数值留「待完善」。

## 2. 配表

- **先问什么**：游戏里有哪些要调的数字（关卡、道具、敌人、掉落）？谁来改表（策划自己改，还是让 Agent 改）？习惯用 Excel / 表格软件，还是直接写 JSON？
- **写到哪里**：`Config/README.md` 的「有哪些表」「格式」「命名」三节：表的清单（每张表一行：管什么、主键）、文件格式（默认 JSON，一张表一个文件）、命名规则（默认 kebab-case，如 `level-list.json`）。有 `Server/` 时，协议和存档格式也在这里定格式。
- **聊不完时**：先定格式和命名，表的清单等玩法定了再补。

## 3. 美术风格

- **先问什么**：题材和世界观？给玩家什么感觉（可爱、热血、安静）？有没有喜欢的参考游戏或画师？谁来出图（自己画、外包、AI 出图）？
- **写到哪里**：按 art-director 的流程定方向，再用 art-bible 写进 `art-direction.md`（先写唯一目标、风格总纲、世界与呈现、色彩系统、反面清单）；`Art/README.md` 补上源文件怎么分目录、参考图和提示词放哪。
- **聊不完时**：风格支柱定了就够，各域细则等第一批资产过审后再补。

## 4. 策划

- **先问什么**：以后一个功能从想法到开发，要写成什么样的文档？需要哪些固定章节（比如数值表、验收问题）？
- **写到哪里**：按用户的回答调整 `.spec/knowledge/features/_TEMPLATE.md` 的章节；没有特别要求就保持现状，删掉这个话题。
- **聊不完时**：保持模板现状即可。

## 5. 测试

- **先问什么**：哪些东西必须有自动测试（默认：规则和数值逻辑）？界面怎么验收（默认：标准尺寸截图）？谁来试玩、多久一次？
- **写到哪里**：`testing.md` 的「游戏项目测什么」，删掉这一节的「待完善」。「项目测试栈与命令」留到建工程时再填。

## 6. 工作流

- **先问什么**：提交信息用什么语言？要不要每个功能都先写计划再派 Agent？有没有哪些模块改动必须深审？
- **写到哪里**：`workflow.md` 的「怎么派 Agent」和提交规范里需要调整的地方，删掉「待完善」。分支和合并方式第一段已经按人数定了，用户想改再改。

## 7. 其他规范

- **先问什么**：代码风格有没有特别的要求（缩进、命名、用不用某个格式化工具）？有没有绝对不能做的事，要写成项目红线？
- **写到哪里**：`code-style.md` 的「语言 / 框架特定风格」；新的红线用 spec-steward 加进 `.spec/rules/project.md`（一条一节，只写「必须 / 只能 / 不得」）。格式化工具的配置等建工程时再加。
